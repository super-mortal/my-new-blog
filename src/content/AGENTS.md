# AGENTS.md — supermortal.cn 文章写作规范

本文件用于指导 AI（以及作者本人）在看到写作需求时，按本博客统一的风格、结构与 frontmatter 规范生成文章。所有新文章都应先过一遍本规范。

## 博客定位

- 个人技术博客，读者是正在学习或准备动手的开发者/爱好者
- 内容以实战教程、踩坑记录、部署运维、AI 开发、服务器安全为主
- 价值点是“照着做就能复现”：每一步都给命令、配置、结果或截图
- 语气真诚、口语化但不拖沓，不写空话和营销腔

## 写作风格（从现有 20 篇文章提炼）

1. **开头直给问题**：用一两句话说明“这篇文章解决什么”，不要大段寒暄
2. **叙事身份**：以作者第一人称“我”展开，允许记录真实踩坑过程，但最终要收敛到可复用结论
3. **结构清晰**：使用 `##` 分大节、`###` 分小节；步骤用有序/无序列表，关键命令用代码块
4. **每步可验证**：执行后给出预期输出、页面现象、检查命令或截图，方便读者确认
5. **适当总结**：结尾用简短“写在最后/小结”收尾，列出复盘点或下一步方向
6. **不堆术语**：首次出现的概念给一句人话解释，再进入具体操作
7. **截图配图**：关键界面/报错/成果用图片佐证；图片放文章同目录，正文用相对路径 `./01.png`
8. **常见问题**：长教程建议加 FAQ/常见报错小节，直接给解决方案
9. **开头给结论**：长文在标题后、展开细节前，先给一段能独立成文的一句话答案或摘要，方便检索和 AI 直接引用

## Markdown 规范

- 标题从 `##` 开始（`#` 只在文章正文首行使用一次，一般省略）
- 代码块必须标注语言，如 `bash`、`docker`、`markdown`、`python`
- 行内命令、文件名、环境变量用反引号包裹
- 强调少用加粗堆砌，最多对关键按钮/概念加粗
- 列表层级不超过两层
- 提示/警告使用 GitHub Admonitions：
  - `> [!NOTE]` 补充说明
  - `> [!TIP]` 操作建议
  - `> [!WARNING]` 风险提醒
  - `> [!CAUTION]` 高危险操作
- 外链不加 `target`，由主题统一处理；内部链接使用站内绝对路径 `/blog/...`

## Frontmatter 规范

```yaml
---
title: '不超过 60 字的标题'
slug: '英文-kebab-case，如 deploy-openclaw-on-linux'
description: '不超过 160 字，说明文章要解决什么问题'
publishDate: 2026-09-06
tags:
  - 标签1
  - 标签2
language: '中文'
category: 教程
---
```

- `title`：准确、有行动指向（“部署 X”“学会 Y”“排查 Z”）
- `slug`：固定英文小写短横线格式，一旦发布不要随意修改，避免外链失效
- `description`：像搜索结果摘要，包含关键词和结果承诺
- `tags`：2~4 个；避免每个账号都用“教程”这类形式标签刷屏
- `category`：单值，一篇文章只归一个分类（可选，不填默认“未分类”）
- `language`：通常 `中文`

## 写作流程建议（给 AI）

1. 先确认主题属于博客领域（教程/运维/AI/项目/踩坑），不符合则先说明
2. 列出大纲：背景 → 前置准备 → 分步骤实操 → 验证结果 → 常见问题/总结
3. 写作时保持信息密度，代码与截图必须有实际来源，禁止编造命令输出
4. 完成后自检：frontmatter 是否齐全、步骤是否可复现、代码块语言是否正确、图片路径是否存在
5. 涉及外部服务/版本号时注明日期和环境，避免过期信息误导

## 禁止事项

- 禁止编造不存在的命令输出、报错或截图
- 禁止把搜索到的二手结论当成自己验证过的结果
- 禁止发布未验证的“最佳实践”或安全建议（尤其涉及删除、格式化、生产环境）
- 禁止在正文加入“本文由 AI 生成”“仅供参考”等影响专业感的文案
- 禁止出现未定义的连接词堆砌（“综上所述/众所周知”），保持直接
